# MerchantMind｜项目面试讲解稿

## 30 秒版本

我做的是 MerchantMind，一款面向中小商家的 AI 经营诊断工具。商家上传经营周报、按天记录、商品和评价数据后，系统将数据转成趋势、异常证据和 P1—P3 行动优先级，并支持记录进度、复盘和导出行动方案。核心设计是可解释优先：大模型不可用时，规则引擎仍能给出基于当前数据的建议。

## 2 分钟版本

### 1. 为什么做

中小商家通常能看到 GMV、转化、评分等数字，却很难快速判断下一步先改什么。单纯给一段 AI 建议也不可靠，因为数据不足或模型不可用时，结论容易失去依据。

### 2. 我怎样拆解问题

- 将数据分为经营汇总、按天记录、商品明细和顾客评价四类；它们分别服务于全局指标、趋势定位、商品机会与体验证据。
- 用按天记录计算多周期趋势与当前周期对比上一周期；缺少足够历史数据时明确提示，而不生成虚假的长期结论。
- 将诊断结果收敛为 P1—P3 行动队列，并为每项行动设置后续验证指标，避免“发现问题但无法执行”。

### 3. 关键实现

- 使用 React、TypeScript 和 Next.js / Vinext 构建多工作区界面。
- 在浏览器解析并校验 CSV：兼容带引号的字段、百分比的两种写法、日期格式、数值范围和重复日期。
- 健康度由转化率、复购率、外卖评分动态计算；趋势对比、异常日期和低分评价共同作为诊断证据。
- 通过服务端 API 路由可选接入 OpenAI 问答；发生额度或服务异常时，自动回退到规则版分析。
- 本地保存上传数据、行动进度和复盘记录，刷新页面后可继续使用。

### 4. 如何与 AI coding assistant 协作

我不是只让 AI 生成一个页面，而是先明确用户、数据字段与诊断边界，再按“数据上传—分析—行动—复盘”的闭环拆分任务。我会检查 AI 生成结果是否符合业务逻辑，例如上传的 8.5% 转化率不应被误判为低于 8%，且案例数据不能冒充商家的真实数据。每次功能完成后运行测试、构建和代码检查，再用 GitHub 留下可追溯的迭代记录。

## 高频追问

### 为什么不完全依赖大模型？

经营诊断需要稳定、可解释。核心优先级使用明确的指标规则生成，大模型只负责开放式问答和补充表达；没有 API 额度时，商家仍可完成核心诊断。

### 为什么要把四类数据分开上传？

经营周报回答“整体表现如何”；按天数据回答“哪天、哪个环节变化”；商品明细回答“哪个商品有机会或风险”；评价数据补充“顾客为什么不满意”。将它们混成一张表会提高商家准备数据的成本，也会让结论失去边界。

### 如何保证 CSV 上传可靠？

解析前检查表头和必填字段；解析时校验数字、百分比、评分、日期与重复日期；错误信息直接指出缺失字段或问题行。对于带逗号的评价内容，使用支持引号的解析逻辑，避免普通 split 导致数据错列。

### 你做了哪些质量保障？

为 CSV 引号解析、百分比兼容和健康度计算写了 Vitest 自动化测试，并在发布前执行测试、构建和 lint。公开链接和 GitHub 仓库分别用于产品体验和代码过程展示。

### 如果继续迭代，会做什么？

先做真实商家访谈与可用性测试，验证四类数据入口是否足够顺手；随后再考虑平台数据自动同步、账户体系和云端数据存储。当前版本明确采用浏览器本地保存，避免在没有真实用户验证前过早建设复杂后端。

## 演示时的注意点

- 先演示问题闭环，再讲技术：数据上传 → 异常证据 → P1 行动 → 导出/复盘。
- 面试官问 AI 时，强调“规则可解释、模型可选、故障可降级”，不要把项目描述成完全依赖模型的聊天机器人。
- 只描述真实实现和真实验证，不把案例数据说成线上商家真实效果。
